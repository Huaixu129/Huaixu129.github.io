1. 计算机网络

粘包、拆包

粘包： tcp流式传输、没有边界，可能算法导致，可能接收方缓冲区堆积导致

拆包： 超过MSS(最大报文长度)、MTU(最大传输单元)都，TCP/IP协议栈对其分片

TCP三次握手四次挥手

TCP三次握手：确认双方的通信能力

  • 第一次：客户端发起报文, SYN=1, ACK=1，随机初始化传输序号seq=x

  • 第二次：服务端发起报文，SYN=1, ACK=1，随机初始化传输序号seq=y，ack指定期望下次收到的序号x+1

  • 第三次：客户端发起报文，ACK=1, seq=x+1,ack=y+1。客户端进入established，服务端也进入established

TCP四次挥手：确认话说完了

  • 第一次：客户端发起报文，FIN=1, seq=x, 并停止发送数据，客户端进入FIN_WAIT_1

  • 第二次：服务端发起报文，ACK=1, ack=x+1, 表示收到了，请等待，服务器进入关闭等待

  • 第三次：服务端发起报文，FIN=1, seq=y，表示我也挂了，服务器进入最后确认，客户端进入FIN_WAIT_2

  • 第四次：客户端发送报文进入TIME_WAITING

全双工半双工单工解释

单工：消息只能一方发往另一方

半双工：在同一时刻，信道上只能有一个方向的数据流动，双方必须交替地进行发送和接收。

全双工：两条信道，互不影响

HTTP是什么(1.0 1.1 2.0 3.0全双工)

HTTP 超文本传输协议

默认端口80

  • HTTP1.1 引入长连接，但是穿行传输没有解决(队头阻塞)

  • HTTP2.2 引入Stream, 实现多路服用，交错并发地在一个TCP连接流动。引入Head Pack重复的head不再重复发出，用客户端共同维护的索引表替代。引入服务端推送，比如请求html, 自动推送css(被废弃，太耗带宽)。并没有完全解决多路复用，TCP上要求按序到达，一旦丢包，还是可能造成堵塞(解决方法：魔改UDP)

  • HTTP3.3 底层改用UDP, 应用层的QUIC协议来保证可靠传输和流量控制。QUIC把传输连接和加密连接结合在一起。使用connection_id来标记一次连接，防止网络切换导致连接失败。HPACK变成QPACK, 乱序到达也能拼好

time_waited作用

分手前的冷静期

QUIC 的握手时间为什么短

合并了连接建立与加密协商（首次连接 1-RTT） 在传统的 HTTPS 通信中，必须严格分步进行：先进行 TCP 的三次握手建立网络连接（耗时 1.5 RTT），然后再进行 TLS 握手协商加密密钥（TLS 1.2 需 2 RTT，TLS 1.3 需 1 RTT），整体加起来通常需要 3 到 4 个 RTT。
而 QUIC 是基于无连接的 UDP 协议的，它巧妙地将“建立连接”和“TLS 1.3 密钥协商”合并到了同一个过程中。客户端在发送第一个握手包时，就把连接请求和加密参数一起发了过去。因此，QUIC 首次建立安全连接只需要 1 个 RTT。

对java stream有什么了解

Stream 是 Java 8 引入的一种基于函数式编程的 API，主要用于对集合（Collection）或数组进行高效、链式的数据处理。需要强调的是，Stream 本身不存储数据，也不改变底层的数据源，它更像是一条“流水线”，专门负责对流入的数据进行各种计算和转换。
