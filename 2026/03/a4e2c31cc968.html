HashMap的底层原理

HashMap什么结构

HashMap的内部使用的数组进行存储，在解决Hash冲突上采用的是拉链法，在也就是使用链表解决冲突，并且为了提高冲突时的查询效率，在Jdk8引入了红黑树

HashMap扩容机制

HashMap 的扩容机制核心由负载因子（默认 0.75）和容量（默认初始 16，且始终为 2 的幂）共同决定：

  1. 当 HashMap 中实际存储的键值对数量（size）≥ 阈值（threshold = 容量 × 负载因子），且插入新元素时，触发扩容；
  2. 扩容时容量翻倍（旧容量 ×2），同时重新计算阈值；
  3. 扩容需要对元素做 rehash 迁移：JDK7 中需逐个重新计算 hash 值确定新位置，效率较低；JDK8 做了优化，通过e.hash & oldCap判断 —— 结果为 0 则元素留在原索引位置，结果为 1 则迁移到 “原索引 + 旧容量” 的新位置，且先计算好所有元素的新位置再统一迁移，提升了效率。

如何确定索引

(n - 1) & hash 等价于取模，效率更高

hash怎么得到的?

(h = key.hashCode()) ^ (h >>> 16)

HashMap 不会直接用 key.hashCode() 作为最终 hash，而是做了哈希扰动处理：

  • 第一步：调用 key.hashCode()（native 方法，返回一个 int 型的哈希值，范围 -2^31 ~ 2^31-1）；
  • 第二步：将这个哈希值的高 16 位右移 16 位（h >>> 16），再与原哈希值做位异或（^）；
  • 目的：让哈希值的高 16 位和低 16 位充分混合，减少哈希冲突（因为后续计算索引只用到低几位，高 16 位参与运算能提升散列性 h >>> 16`, hashCode是一个native函数

PriorityQueue底层原理

PriorityQueue 在 Java 里是用小顶堆实现的，底层是个 Object 数组。数组下标从 0 开始，对于任意节点 i，左孩子是 2i+1，右孩子是 2i+2，父节点是 (i-1)/2。这样存完全二叉树不需要指针，省内存。

插入元素的时候，先扔到数组末尾，然后做 siftUp：跟父节点比，如果更小就交换，一路浮上去，直到比父节点大或者到根。复杂度 O(log n)。

取队首的时候，把根节点（array[0]）记下来，然后把最后一个元素挪到根的位置，数组 size 减一，再做 siftDown：跟左右孩子里较小的那个比，如果比孩子大就下沉，直到找到合适位置。也是 O(log n)。

这里有个细节，扩容策略：默认初始容量 11，满了之后不是简单的 2 倍扩。如果原容量小于 64，就扩到 2n+2；大于 64 就 1.5 倍扩。小容量时多给点，避免频繁扩容；大容量时保守点，省内存。

JVM

JVM内存模型

JVM的运行时数据区被分成了五块：堆、方法区、虚拟机栈、本地方法栈、程序计数器。堆和方法区是线程共享、另外是线程私有的。

  • 堆是内存分配最大的区域，new出来的对象和数组都放在堆里。GC主要也是在堆上进行。

  • 方法区主要存储类的元信息，包括类结构、常量池、静态变量、JIT编译后的代码(热点代码编译成机器码)缓存。JDK8之前用永久代(永久代在堆内存里)实现、JDK8换成了元空间，直接使用系统内存、上限更高

  • 虚拟机栈：线程私有，每调用一个方法将压一个栈帧(局部变量、操作数等)、执行完就弹出来。

  • 本地方法栈：和虚拟机栈差不多，但是调用的是native方法，也就是C/C++写的JNI代码

  • 程序计数器：记录当前线程执行到哪个字节码指令里，方便线程切换回来的时候继续执行

如果一个对象具有强引用，那就类似于必不可少的生活用品，垃圾回收器绝不会回收它。当内存空间不足，Java 虚拟机宁愿抛出 OutOfMemoryError 错误，使程序异常终止，也不会靠随意回收具有强引用的对象来解决内存不足问题。

软引用对象在内存压力较大时可能会被回收，但JVM不保证只在内存不足时才清理。

3．弱引用（WeakReference）

如果一个对象只具有弱引用，那就类似于可有可无的生活用品。弱引用与软引用的区别在于：只具有弱引用的对象拥有更短暂的生命周期。在垃圾回收器线程扫描它所管辖的内存区域的过程中，一旦发现了只具有弱引用的对象，不管当前内存空间足够与否，都会回收它的内存。

4. 虚引用（PhantomReference）

虚引用主要用来跟踪对象被垃圾回收的活动。

"虚引用"顾名思义，就是形同虚设，与其他几种引用都不同，虚引用并不会决定对象的生命周期。如果一个对象仅持有虚引用，那么它就和没有任何引用一样，在任何时候都可能被垃圾回收。

虚引用必须和引用队列（ReferenceQueue）联合使用。

垃圾回收

Java内存分配以及回收原则

对象优先在Eden区(新生代)中分配, 大对象直接进入老年代，长期存活的对象进入老年代

大部分情况，对象都会首先在 Eden 区域分配。如果对象在 Eden 出生并经过第一次 Minor GC 后仍然能够存活，并且能被 Survivor 容纳的话，将被移动到 Survivor 空间（s0 或者 s1）中，并将对象年龄设为 1(Eden 区->Survivor 区后对象的初始年龄变为 1)。

对象在 Survivor 中每熬过一次 MinorGC,年龄就增加 1 岁，当它的年龄增加到一定程度（默认为 15 岁），就会被晋升到老年代中。

垃圾回收算法

标记清除算法，复制算法，标记整理算法、分代收集算法

当前虚拟机的垃圾收集都采用分代收集算法，这种算法没有什么新的思想，只是根据对象存活周期的不同将内存分为几块。一般将 Java 堆分为新生代和老年代，这样我们就可以根据各个年代的特点选择合适的垃圾收集算法。

Parallel Scavenge 收集器

这是 JDK1.8 默认收集器

Parallel Scavenge 收集器关注点是吞吐量（高效率的利用 CPU）。

新生代采用标记-复制算法，老年代采用标记-整理算法。

CMS

CMS（Concurrent Mark Sweep）收集器是一种以获取最短回收停顿时间为目标的收集器。

CMS 收集器是一种 “标记-清除”算法实现的

主要优点：并发收集、低停顿。但是它有下面三个明显的缺点：

  • 对 CPU 资源敏感；
  • 无法处理浮动垃圾；
  • 它使用的回收算法-“标记-清除”算法会导致收集结束时会有大量空间碎片产生。

G1

G1 (Garbage-First) 是一款面向服务器的垃圾收集器,主要针对配备多颗处理器及大容量内存的机器. 以极高概率满足 GC 停顿时间要求的同时,还具备高吞吐量性能特征。

G1 收集器在后台维护了一个优先列表，每次根据允许的收集时间，优先选择回收价值最大的 Region(这也就是它的名字 Garbage-First 的由来)

JMM

JMM是JVM定义的一套规范，规定变量在内存中如何存储和传递，以及线程何时读写主存

核心目标是确保多线程环境下的可见性(volatile)、有序性(Happen-Before)和原子性(synchronized)

AQS

AQS(AbstractQueuedSynchronized) 是Java包里的锁和同步器的基本框架。

AQS有两个核心，一个是volatile int 的status变量，另一个是双向链表实现的FIFO队列。

state 表示资源状态，具体含义由子类定义。ReentrantLock 里 state 表示锁被重入了多少次，CountDownLatch 里 state 表示还剩多少计数。

线程想获取资源，先 CAS 改 state，成功了就拿到资源，失败了就包装成 Node 节点加入队列尾部，然后 park 挂起等着。前面的线程释放资源后会unpark唤醒队列里的后继节点。

AQS 把排队、阻塞、唤醒这些脏活累活都封装好了，子类只需要实现 tryAcquire、tryRelease 这几个方法，告诉 AQS 什么时候算拿到资源、什么时候算释放资源就行。

ConcurrentHashMap的演进

jdk1.7采用分段锁的设计，底层把数组默认分成了16个segment, 然后线程写时锁住对应的segment, 并发度固定。

jdk1.8移除了segment, 数据结构和HashMap同步， 数组+链表+红黑树。插入时先尝试CAS无锁插入，冲突了采用synchronized，并且只锁链表或树的头节点，并发度有保障。

线程池

线程池原理

线程池是一种池化技术，核心思想就是复用线程，避免每来一个任务就 new一个 Thread。创建销毁线程的开销不小，一个线程起码占用 1MB 左右的栈空间，还有操作系统层面的调度成本。
线程池有几个关键参数：核心线程数、最大线程数、空闲存活时间、工作队列、拒绝策略。

拒绝策略

很少使用内置的拒绝策略，更多是实现RejectExcutionHandler做定制

设计的时候要考虑四个核心问题：线程怎么管理、任务怎么存储、满了怎么拒绝、怎么监控。
